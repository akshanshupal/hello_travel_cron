# Deployment Guide

This guide deploys the HelloTravel lead worker on a Linux server. The worker polls HelloTravel every 30 seconds, forwards new leads to Neodove, and stores datewise CSV files in the `leads` directory.

## 1. Server requirements

Install:

- Node.js 18 or newer
- `cron` or `cronie`
- SSH access

Check the installed versions:

```bash
node --version
crontab -l
```

Node.js 18+ is required because the worker uses the built-in `fetch` API.

## 2. Copy the project to the server

From the local machine, copy the project to the server. Replace `SERVER_USER` and `SERVER_HOST`:

```bash
rsync -avz --exclude='.env' --exclude='data/' --exclude='leads/' --exclude='worker.log' \
  /Users/akshanshupal/Projects/Backend/hello_travel_lead_cron/ \
  SERVER_USER@SERVER_HOST:/home/ubuntu/hello_travel_cron/
```

Log in to the server:

```bash
ssh SERVER_USER@SERVER_HOST
```

Go to the project directory:

```bash
cd /home/ubuntu/hello_travel_cron
```

## 3. Create the production environment file

Create `.env` on the server:

```bash
nano /home/ubuntu/hello_travel_cron/.env
```

Use the production HelloTravel URL and API key supplied by HelloTravel:

```env
POLL_INTERVAL_SECONDS=30

HELLOTRAVEL_URL=https://ihook.hellotravel.com/modal/hookleadapi.php
HELLOTRAVEL_API_KEY=YOUR_HELLOTRAVEL_PRODUCTION_API_KEY

NEODOVE_URL=https://05477313-6db9-4b4f-8bab-0847fa88bf45.neodove.com/integration/custom/b4f84b54-e1b0-464c-9139-f5565c95ec07/leads

LEADS_DIR=/home/ubuntu/hello_travel_cron/leads
STATE_DIR=/home/ubuntu/hello_travel_cron/data

REQUEST_TIMEOUT_SECONDS=20
MAX_FORWARD_ATTEMPTS=3
```

Protect the environment file:

```bash
chmod 600 /home/ubuntu/hello_travel_cron/.env
```

Do not commit or publicly expose `.env` because it contains API credentials.

## 4. Prepare directories and permissions

```bash
mkdir -p /home/ubuntu/hello_travel_cron/leads
mkdir -p /home/ubuntu/hello_travel_cron/data
chmod +x /home/ubuntu/hello_travel_cron/run_worker.sh
```

Make sure the user running cron owns the application files:

```bash
sudo chown -R "$USER":"$(id -gn)" /home/ubuntu/hello_travel_cron
```

## 5. Test manually before enabling cron

Run the worker in the foreground:

```bash
/home/ubuntu/hello_travel_cron/run_worker.sh
```

Expected output includes:

```text
Starting worker; polling every 30 seconds
Fetched ... lead(s) from HelloTravel
Forwarded and saved lead ...
```

Stop the worker after confirming that the lead reached Neodove:

```text
Ctrl+C
```

Check the generated files:

```bash
ls -la /home/ubuntu/hello_travel_cron/leads
ls -la /home/ubuntu/hello_travel_cron/data
```

A successful lead file looks like:

```text
/home/ubuntu/hello_travel_cron/leads/leads-YYYY-MM-DD.csv
```

The duplicate protection state is stored at:

```text
/home/ubuntu/hello_travel_cron/data/processed_leads.json
```

## 6. Configure automatic restart after server reboot

The worker is a long-running process that polls every 30 seconds. Use cron only to start it once after boot; do not configure a cron entry every 30 seconds.

Edit the crontab for the same server user that owns the application:

```bash
crontab -e
```

Add:

```cron
@reboot /home/ubuntu/hello_travel_cron/run_worker.sh >> /home/ubuntu/hello_travel_cron/worker.log 2>&1
```

Save and verify the entry:

```bash
crontab -l
```

This starts the worker automatically whenever the server restarts. The worker then continues polling every 30 seconds.

## 7. Verify the running process

Check whether the worker is running:

```bash
pgrep -af 'hello_travel_lead_worker.js'
```

View worker logs:

```bash
tail -f /home/ubuntu/hello_travel_cron/worker.log
```

Check the latest CSV file:

```bash
ls -t /home/ubuntu/hello_travel_cron/leads/leads-*.csv | head -n 1
```

## 8. Restart the worker manually

Stop the current worker:

```bash
pkill -f 'hello_travel_lead_worker.js' || true
```

Start it again:

```bash
/home/ubuntu/hello_travel_cron/run_worker.sh >> /home/ubuntu/hello_travel_cron/worker.log 2>&1 &
```

The worker keeps processed lead IDs in `data/processed_leads.json`, so restarting it does not resend leads that were already successfully forwarded.

## 9. Important operational notes

- Keep the server clock accurate because CSV filenames use the server date.
- Keep `data/processed_leads.json`; deleting it can cause already-forwarded leads to be sent again.
- Keep the `leads` directory backed up if the CSV files are important.
- The HelloTravel sandbox returns static test leads. Use the production HelloTravel URL and API key for live lead ingestion.
- Ensure outbound HTTPS access to both HelloTravel and Neodove is allowed by the server firewall.
- If using a cloud server, configure log rotation for `worker.log`.
